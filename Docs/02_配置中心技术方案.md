# 《昆吾禁地》配置中心技术方案

> 文档状态：首期实施基线  
> 对应产品方案：`Docs/01_配置后台产品方案.md`  
> 技术范围：`KunWuAdmin` 配置数据库、发布服务、配置 API 与 `KunWuGodot` 客户端接入

## 1. 总体设计

采用“关系型编辑源 + 不可变发布快照 + 客户端模块包”的三层模型：

```text
配置人员
   │
   ▼
KunWuAdmin / Next.js
   ├── 管理 API、领域校验、导入导出
   ├── 配置编译器、差异、发布与回滚
   │
   ▼
MySQL 8
   ├── 可编辑业务表
   ├── 配置集、权限与审计
   └── 不可变发布快照
   │
   ▼
只读 Game Config API
   │
   ▼
KunWuGodot
   ├── 下载清单和变化模块
   ├── 校验、缓存、原子切换
   └── 失败时回退上次完整版本或 res:// 内置配置
```

Godot 不感知数据库表结构。发布编译器是后台模型与客户端 Schema 之间唯一的转换边界。

## 2. 技术选型

| 层 | 首期选型 | 说明 |
|---|---|---|
| 管理后台 | Next.js 15、React 19、TypeScript | 复用当前项目 |
| 数据库 | MySQL 8.4 LTS（最低 8.0.34） | InnoDB、事务、JSON、CHECK、成熟托管与备份能力 |
| ORM/迁移 | Drizzle ORM + drizzle-kit | 使用 `mysql-core`，保留 SQL、索引和约束的可见性 |
| 数据库驱动 | `mysql2` | 服务端连接池；事务期间固定使用同一连接 |
| 参数校验 | Zod | 管理 API、导入文件和编译输出共用 Schema |
| 身份认证 | Auth.js + 数据库 Session | 首期账号密码或受信任 OAuth，生产禁用匿名写入 |
| 密码哈希 | Argon2id | 仅在使用本地账号密码时需要 |
| 日志 | 结构化 JSON 日志 | 携带 requestId、userId、configSetId、releaseId |
| 测试 | Vitest + Playwright | 领域校验、API、发布事务和关键后台路径 |

首期发布产物直接存 MySQL；当产物规模或下载量明显增长时，再把不可变模块包迁移到对象存储，
数据库继续保存元数据、哈希和对象地址。首期不引入 Redis、消息队列和微服务。

## 4. 数据库设计原则

### 4.1 通用字段

可编辑业务表默认包含：

```text
id              binary(16) primary key
config_set_id   binary(16) not null
code            varchar(96) not null
status          varchar(16) not null  -- active / disabled
sort_order      integer not null default 0
revision        integer not null default 1
created_at      datetime(3) not null
created_by      binary(16) not null
updated_at      datetime(3) not null
updated_by      binary(16) not null
notes           text null
```

业务稳定引用使用 `(config_set_id, code)`；内部关联和审计使用应用层生成的 UUIDv7，并以
`binary(16)` 保存。每个业务表建立
`unique(config_set_id, code)`。更新时要求 `WHERE id = ? AND revision = ?` 并令 revision 加一，受影响
行数为零即返回编辑冲突。

数据库、连接与排序统一要求：

- 存储引擎固定为 InnoDB；
- 数据库默认字符集为 `utf8mb4`，业务文本使用 `utf8mb4_0900_ai_ci`；
- `code`、版本号、哈希和枚举字段使用 ASCII 或 binary collation，保证稳定 ID 大小写敏感；
- 数据库 Session 固定 `time_zone = '+00:00'`，应用与 API 只交换 UTC；
- 开启严格 SQL Mode，至少包含 `STRICT_TRANS_TABLES`、`NO_ZERO_DATE` 和 `ERROR_FOR_DIVISION_BY_ZERO`。

### 4.2 类型策略

- 频繁变化的业务枚举使用 `varchar + CHECK` 或字典表，避免数据库 enum 的迁移负担；
- 金额、数量、Tick、百分比基点使用整数，禁止浮点累计；
- 时间使用 UTC `datetime(3)`；只有确实需要自动更新时间的字段才使用数据库默认值；
- 七维列使用确定的整数列，便于约束、查询和差异；
- 条件树、剧情图、地图地形和复杂效果参数使用 MySQL `json`，并经过 Zod/JSON Schema 校验；
- 需要筛选的 JSON 路径通过生成列或函数索引显式建立索引；高频关联仍使用子表；
- 不在数据库保存可执行 JavaScript、SQL 或 GDScript。

### 4.3 删除策略

业务配置只允许停用，不物理删除。尚未被任何发布和其他配置引用的误建草稿可由管理员清理，但
操作必须写入审计。发布、审计、修订和校验记录永不级联删除。

## 5. 系统与发布表

### 5.1 身份与权限

| 表 | 核心字段 |
|---|---|
| `admin_user` | `id, email, display_name, password_hash, status, last_login_at` |
| `admin_role` | `id, code, name` |
| `admin_user_role` | `user_id, role_id` |
| `admin_session` | 由 Auth.js Adapter 管理的 Session 字段 |

权限在 service 层按动作校验，例如 `config.read`、`config.write`、`release.build`、
`release.production`、`release.rollback`、`system.manage`。

### 5.2 配置集

`config_set`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | binary(16) | UUIDv7 主键 |
| `code` | varchar(64) unique | `demo_d0`、`v1_0` |
| `name` | varchar(128) | 显示名 |
| `schema_version` | integer | 当前编辑模型对应的客户端 Schema |
| `current_revision` | bigint | 任一业务保存时原子递增，校验与发布据此判定是否过期 |
| `base_release_id` | binary(16) null | 从哪个发布复制 |
| `status` | varchar(16) | active / archived |
| `created_at/by` |  | 审计 |

所有业务引用必须确保双方 `config_set_id` 相同。对于普通外键可使用复合外键；JSON 内引用由发布
校验器保证。

### 5.3 修订和审计

| 表 | 作用 |
|---|---|
| `config_entity_revision` | 保存每次业务实体保存前后的 JSON 快照、修订号和操作者 |
| `audit_log` | 登录、导入、保存、停用、校验、发布、晋级、回滚等行为 |

`config_entity_revision` 核心字段：

```text
id, config_set_id, entity_type, entity_id, entity_code,
revision, operation, before_data json, after_data json,
changed_by, changed_at, request_id
```

实体写入与修订/审计必须处于同一事务。

### 5.4 校验

| 表 | 核心字段 |
|---|---|
| `config_validation_run` | `id, config_set_id, source_revision, status, error_count, warning_count, started_at, finished_at, triggered_by` |
| `config_validation_issue` | `run_id, severity, module_code, entity_type, entity_code, field_path, rule_code, message, details json` |

`source_revision` 是配置集级递增序号。任一业务保存都会增加配置集 revision；只有校验结果的
source_revision 等于当前 revision，才允许构建发布。

### 5.5 导入来源与冲突

| 表 | 核心字段 |
|---|---|
| `config_import_run` | `id, config_set_id, source_kind, source_root, status, started_at, finished_at, triggered_by` |
| `config_import_issue` | `run_id, severity, conflict_type, entity_type, entity_code, candidate_values json, resolution_status, resolved_by, resolution_notes` |
| `config_import_issue_source` | `import_issue_id, source_path, source_pointer, source_hash` |
| `config_entity_source` | `config_set_id, entity_type, entity_id, source_kind, source_path, source_pointer, source_hash, imported_at` |

导入器只能写入目标配置集的草稿，并为每条导入实体保存来源。重复定义、文档与运行值冲突、无法确定
稳定 ID 或无法映射的硬编码进入 issue；未解决的错误级冲突阻止发布，不能用“最后一个文件获胜”。

### 5.6 审核

`config_change_request` 保存一次待审核变更：

```text
id, config_set_id, source_revision, title, description,
status, validation_run_id, submitted_by, submitted_at,
reviewed_by, reviewed_at, review_notes
```

状态为 draft、submitted、approved、rejected、released、superseded。配置集 revision 在提交后发生变化时，
原审核自动变为 superseded；发布只能使用 approved 且 source_revision 仍等于当前配置集 revision 的记录。

警告确认属于审核记录，使用 `config_change_warning_ack(change_request_id, validation_issue_id,
acknowledged_by, reason)` 保存；不能仅依赖浏览器确认状态。

### 5.7 发布

| 表 | 核心字段 |
|---|---|
| `config_release` | `id, channel, sequence, version, schema_version, min_client_version, source_config_set_id, source_revision, change_request_id, status, release_notes, created_by, created_at` |
| `config_release_module` | `release_id, module_code, module_schema_version, sha256 binary(32), byte_size, content_encoding, payload_json json, artifact longblob` |
| `config_channel_head` | `channel, active_release_id, updated_at, updated_by` |

`channel` 首期固定为 `development`、`staging`、`production`。`sequence` 在同一 channel 内严格递增，
清单使用它判断版本新旧。

`config_release_module.artifact` 以 `longblob` 保存 UTF-8 canonical JSON 的 gzip 字节；`payload_json`
用于后台查看和
服务端诊断。SHA-256 对未压缩 canonical JSON 计算，避免不同压缩器造成哈希变化。

晋级到下一环境时，不重新运行编译器，而是复制源发布的模块快照及哈希到目标 channel 的新发布。
回滚同理，因此 sequence 仍然单调递增。

## 7. 索引与约束

所有业务表至少建立：

```sql
unique (config_set_id, code);
index  (config_set_id, status, sort_order);
index  (config_set_id, updated_at desc);
```

子表建立父 ID 和顺序索引。审计、修订和发布表按时间倒序建立索引。MySQL JSON 只为实际查询的
路径建立生成列或函数索引，不对所有 JSON 字段无差别建索引。

数据库 CHECK 示例：

```sql
check (base_interval_ticks > 0);
check (cooldown_ticks >= 0);
check (primary_percent >= 0);
check (field_healing_percent between 0 and 100);
check (material_loss_basis_points between 0 and 10000);
check (quantity_min >= 0 and quantity_max >= quantity_min);
check (status in ('active', 'disabled'));
```

跨行、跨表和条件树规则由领域校验器处理，不能只依赖数据库 CHECK。

## 8. 发布模块与客户端 Schema

首期模块拆分：

| module_code | 内容 |
|---|---|
| `base` | 多语言、资源物品、奖励包、全局参数、新档入口 |
| `progression` | 职业、成长、灵根、境界、修士模板 |
| `combat` | 战斗参数、技能、状态、AI、敌人、遭遇、掉落 |
| `economy` | 建筑、灵源院生产、储量 |
| `expedition` | 整备、休整、物品携带和地图进入规则 |
| `maps` | 地图清单；每张大地图可进一步成为独立子模块 |
| `stories` | 剧情工程、任务和变量定义 |

模块间采用稳定字符串 ID 引用。客户端加载全部必需模块后统一建立索引并校验引用，不能依赖 HTTP
返回顺序。

编译器要求：

1. 查询固定 `source_revision` 的一致性快照；
2. 只编译 active 配置；
3. 按稳定 ID 和顺序字段确定性排序；
4. 去除后台字段、备注、UUID、操作者和时间；
5. 生成 module schemaVersion 和数据；
6. 通过客户端 Zod/JSON Schema；
7. 序列化为 canonical JSON；
8. 计算 SHA-256、字节数并 gzip；
9. 在同一发布事务中保存所有模块和 release 记录。

相同 source_revision 重复构建必须得到相同模块哈希。

## 10. 发布事务

构建发布流程：

1. 从连接池取得一条专用连接，并开启 MySQL InnoDB `REPEATABLE READ` 事务；
2. 锁定配置集构建锁行和目标 channel 发布锁行；
3. 读取当前 config set revision；
4. 确认存在同 revision 的成功全量校验和已批准审核；
5. 编译全部模块并执行 Schema 和引用校验；
6. 写入 release、module、警告确认和审计；
7. 对目标 `config_channel_head` 行执行 `SELECT ... FOR UPDATE`；
8. 在同一事务内更新 release 状态和 channel head；
9. 提交事务，清单 API 开始返回新版本。

任何异常都回滚整个事务，不能留下“清单已切换但模块缺失”的中间状态。编译时间若增长到不适合
持有长事务，应改为“确定性构建暂存产物 + 短发布事务再次核对 source revision”的两阶段流程；
不得把 channel head 更新拆成一个缺少修订复核的独立操作。

使用 `config_publish_lock(lock_key varchar(128) primary key, updated_at datetime(3))` 锁表。配置集或
channel 创建时预置对应锁行；发布事务直接通过 `SELECT ... FOR UPDATE` 锁定下列键，事务期间必须
固定使用同一个连接：

```text
config-set:{config_set_id}:build
channel:{channel}:publish
```

更新 `config_channel_head` 前还要对对应 channel 行执行 `SELECT ... FOR UPDATE`。不依赖 MySQL
`GET_LOCK()`，避免连接池切换或连接断开使锁生命周期不清晰。

晋级和回滚只复制模块快照引用或 artifact，不重新读取业务表。

## 11. 差异实现

差异分两层：

- **实体差异**：当前配置集与目标发布的业务实体增删改，用于策划审核；
- **产物差异**：两个 release module 的 canonical JSON 差异，用于确认客户端实际变化。

高风险字段单独标记：奖励数量、概率、货币成本、阵亡损失、生产周期、技能倍率、Boss 属性、地图
解锁和新档初始资源。

禁止只用数据库更新时间推导差异；发布审核以结构化内容比较为准。

## 12. Godot 客户端接入

### 12.1 本地目录

建议使用：

```text
user://config/
├── active.json
├── releases/{release_id}/manifest.json
├── releases/{release_id}/base.json
├── releases/{release_id}/combat.json
└── staging/{download_id}/...
```

`active.json` 只在新版本所有必需模块下载、解压、哈希、Schema 和引用校验全部通过后原子替换。

### 12.2 加载顺序

```text
读取 active 远端版本
→ 不存在或损坏则读取 res:// 内置版本
→ 异步请求 manifest
→ 比较 channel sequence 和模块哈希
→ 下载变化模块到 staging
→ 校验完整版本
→ 原子切换 active
→ 下次安全入口生效
```

首期建议在启动到营地前完成检查，但设置较短超时；超时直接进入游戏并后台更新。绝不能让配置服务
故障阻塞启动。

### 12.3 运行实例固定版本

创建出征、战斗或剧情实例时记录：

```text
config_release_id
config_sequence
module_hashes
```

恢复存档时优先读取相同 release 的本地缓存。清理旧缓存前必须确认没有存档或活动实例引用；首期可
保留最近 3 个完整版本加所有被存档引用的版本。

### 12.4 兼容性

- manifest schema 不支持：忽略远端版本，使用本地配置；
- `minClientVersion` 高于客户端：不下载并记录升级提示；
- 单个 module schema 不支持：整版拒绝，不能部分切换；
- 未识别的效果类型：整版拒绝，不能静默忽略；
- 回滚 release sequence 仍比当前高，因此客户端按普通新版本处理。

## 13. 安全

### 13.1 管理后台

- 生产环境禁止匿名写入；
- Session Cookie 使用 HttpOnly、Secure、SameSite=Lax/Strict；
- 所有写操作校验权限、Origin 和输入 Schema；
- 登录、发布、回滚和批量导入设置速率限制；
- 数据库账号区分迁移账号和运行账号，运行账号无 DDL 权限；
- 日志和审计不记录密码、Session、数据库 URL 或完整敏感请求头。

### 13.2 客户端配置

游戏配置本身不视为秘密，客户端接口可以公开只读，但必须：

- 只暴露发布快照；
- 校验 SHA-256 和 release/module 关系；
- 限制请求尺寸和不存在资源的探测速率；
- 不把管理字段、用户信息或内部备注编译进产物。

如未来需要防止配置被中间人篡改，在 HTTPS 和 SHA-256 之外增加 Ed25519 清单签名；客户端内置公钥，
私钥只存在发布环境。首期先在数据模型预留 `signature` 和 `key_id` 字段。

## 14. 备份与恢复

- MySQL 每日全量备份，开启 binary log，并保留至少 7 天以支持时间点恢复；
- 生产发布表和业务配置保留不少于 90 天，审计长期保留；
- 每次生产发布额外导出 manifest 和模块 artifact 到独立备份位置；
- 每季度验证一次从空数据库恢复、管理员登录、历史发布下载和回滚；
- 数据库恢复不自动改变客户端活动版本，恢复后先核对 channel head 与完整 artifact。

## 20. 技术验收

1. 全新数据库可以仅通过迁移和 seed 建立，不依赖手工 SQL。
2. 两个配置集允许相同 code 的不同内容，跨集引用会被数据库或校验器拒绝。
3. 任一实体更新同时产生 revision 和 audit，失败时全部回滚。
4. 相同 source revision 重复构建得到完全相同的模块 SHA-256。
5. 任一模块编译失败时，release 和 channel head 均不改变。
6. 晋级与回滚不会重新编译，目标模块哈希与来源历史版本一致。
7. 客户端 API 不可能读取草稿、审核中或构建失败的 artifact。
8. Godot 能完成下载、哈希校验、原子切换、断网回退和不兼容版本拒绝。
9. 导入 D0 后能够列出所有已知重复源和冲突，不静默覆盖。
10. 数据库备份恢复后，当前发布、历史版本、审计和模块下载均可验证。

## 22. M4 审核工作流实施状态（2026-08-12）

配置中心已接入变更单状态机：

```text
draft → submitted → approved → released
                  ↘ rejected
任一未发布状态 + 新配置修订 → superseded
```

- 创建草稿时固定当前配置集 revision，同一 revision 只允许一张活动变更单；
- 提交时必须绑定当前 revision 的最新成功全量校验，存在 error 时拒绝提交；
- warning 必须逐条写入 `config_change_warning_ack`，记录确认原因，不能只保存在浏览器状态；
- 批准时再次核对配置集 revision、绑定校验和全部 warning 确认；驳回必须填写审核意见；
- 技能保存事务会同步把该配置集的 draft、submitted、approved 变更单更新为 superseded；
- development 发布继续复核 approved 变更单绑定的校验是否仍是最新校验，不接受过期审批；
- 创建、提交、警告确认、批准、驳回均写入 `audit_log` 并携带 requestId。

`/config` 的发布流水线已经展示变更单状态、绑定校验、阻断数和警告确认进度，并按状态提供提交、
确认、批准和驳回操作。当前 D0 因两条阻断问题无法提交审核，符合发布门禁预期。
