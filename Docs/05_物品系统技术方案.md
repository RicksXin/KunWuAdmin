# 《昆吾禁地》物品系统技术方案

- 版本：v0.2（补充炼器坊）；日期：2026-09-17。
- 状态：开发前设计，以下新增表、接口和代码目录尚未实现。
- 对应：[物品系统 PRD](04_物品系统PRD.md)。

## 1. 当前代码与设计原则

| 已有实现 | 使用方式与限制 |
| --- | --- |
| `db/schema/base.ts` / `game_asset` | 复用物品稳定 ID 与基础字段，不另建竞争物品目录 |
| `configEntityRevisions`、`auditLogs` | 记录配置变更前后快照、操作者与请求号 |
| `config-change-request.ts`、`config-release.ts` | 复用校验、审核、不可变发布及渠道指针 |
| `config-compiler.ts` 的基础模块 | 已输出 assets；新增可选字典/效果数据，兼容旧客户端解析 |
| `ResourceService` | 已有服务端结算与幂等，但事务封装需重构才能跨域原子使用 |
| `resource_session` | 开发资源会话，不等于完整通用管理员账号集成 |
| Godot `game.gd` 的 `profile.inventory` | 存在本地直接写入，必须建立逐项替换清单 |

所有数据库修改是增量迁移；不改既有稳定 code、不覆盖历史发布、不自动把本地存档余额当可信数据导入。旧总技术方案中的规划能力不视为现有实现。

## 2. 架构

```text
后台物品/品级编辑
  → 管理员身份与配置集权限 → 关系型草稿 → 校验/审核 → 不可变发布
                                                         ↓
                                  客户端配置缓存 ← 配置清单/基础模块
                                                         ↓
玩家会话 → InventoryService → 固定配置版本 + 玩家上下文 + 事务协调器
                                ├─ 物品余额/待领取
                                ├─ ResourceService 的连接内结算函数
                                └─ 物品/资源流水 + 幂等结果
                                                         ↓
                                          C 端使用响应与权威状态
```

配置控制面与玩家运行态分离。运行时从明确的发布快照读取物品，不读取草稿。各环境映射到明确配置集及配置发布 ID；玩家客户端不能任意选择配置集或环境。

## 3. 配置模型

### 3.1 品级

使用唯一内部方案 `unified`，适用分类及用途为 `all`；后台不开放新增方案。

`item_quality` 每配置集固定六行：`fa_qi`、`zhen_bao`、`fa_bao`、`gu_bao`、`tong_tian_ling_bao`、`xuan_tian_zhi_bao`，分别对应法器、真宝、法宝、古宝、通天灵宝、玄天之宝。

- 名称、编码、排序 0–5、启用状态由共享契约固定，接口拒绝第七档和对固定字段的修改。
- 展示颜色接受 `#RRGGBB`，可以随草稿审核发布。
- 不引入按分类独立的品级字典或适用关系表；未分级物品的 qualityCode 可空。
- 迁移工具在配置集锁内创建六档、迁移资产引用及样例名称、停用旧字典，记录前后快照及审计，递增配置集修订并使旧审核失效。旧发布快照不修改。
- 旧开发样例按档位映射，五档铁胚映射前五级、四档资源包映射前四级；不推算新成本，不自动补充第六级物品或配方。未知旧编码使整笔迁移回滚。

### 3.2 物品

保留 `game_asset` 的 code、nameKey、assetType、qualityCode、iconPath、stackLimit、weight、storageKind、isProtected、isDiscardable、isTradeable、status、revision。

新增 `item_definition` 作为一对一扩展：

| 字段 | 类型/约束 | 说明 |
| --- | --- | --- |
| asset_id | PK/FK game_asset | 复用原资产身份 |
| category_code / usage_tag | 受限字符串 | 新分类和用途；不盲目改写旧 assetType |
| description_key | varchar(160), nullable | 复用 i18n 文本 |
| hold_limit | bigint unsigned | 账号每 ID 持有上限，JSON 中传十进制字符串 |
| unique_owned | boolean | 唯一物要求 hold_limit=1 |
| acquisition_enabled | boolean | 控制新投放，停投不阻止消耗已有库存 |
| use_enabled | boolean | 紧急正常版本内使用开关，独立于停投状态 |
| use_context | enum | none / camp；特殊野外行为在场景适配后开放 |
| allow_batch | boolean | 是否允许一次多件 |
| effect | JSON | 受 Zod 判别联合约束，不是脚本 |

一期 `grant_resource` 效果为单目标 `{type, resourceCode, amountPerUnit}`；resourceCode 必须存在于已接通资源域，amountPerUnit 为正整数字符串。无效果物品用 `{type:"none"}`。钱包、解锁蓝图、装备实例行为在适配完成前发布校验拒绝。

持有上限与 stackLimit 分开。当前数量型库存可按总量存储，C 端堆叠只是展示，服务端始终按总持有量校验。

qualityCode 可空；若非空，必须引用同配置集内适用且启用的品级。名称与描述编辑和对应 i18n 行同事务保存。已有资产没有扩展行时按旧只读资产处理，不自动猜测归类、品级和可用效果。

### 3.3 生命周期

- 已被引用、发布或持有的 code 不可改；复制必须使用新 code。
- 首期不提供物理删除接口；禁用保留定义和历史引用。
- 六个品级不得停用或改名改序，物品可改选六档之一或未分级。
- 既有物品变更分类、存放区域、唯一性需迁移影响校验，不能仅改前端字段。
- 降低持有上限允许保留超限数量，限制新增；不可自动截断余额。

### 3.4 炼制配方与坊级配置

复用已有 building 定义中的炼器坊身份。先核对现有 building_level 数据/升级结构能否完整表达费用与解锁关系；新增配方实体，不以无结构 JSON 替代所有引用。

新增 `craft_recipe`：id、config_set_id、code、name_key、status、availability（ready / planned）、unlock_kind（workshop_level / external_blueprint）、required_workshop_level、blueprint_code、output_kind（stack_item / random_item / equipment / permanent_upgrade）、output_asset_id、output_quantity、allow_batch、max_batch、revision。ready 配方必须有完整成本、产物与已实现处理器；planned 配方允许材料未定，但禁止发布为可执行。

新增 `craft_recipe_cost`：recipe_id、cost_kind（resource / item / currency）、asset_code、quantity、sort_order；同配方账本类型与 code 唯一。所有数量采用正整数字符串契约，明确区分灵晶资源与灵石货币。使用效果与打造配方分别建模，拥有物品不等于可以任意消耗它去炼制。

新增/扩展 `workshop_level_unlock`：config_set_id、level、target_kind、target_code。级别为 1–24；费用写入既有等级表或经审计迁移后的统一等级表，不重复保留两套有效成本。制式蓝图由等级派生或持久化解锁，但只采用一个权威判定函数。

一期执行白名单：五档铁胚、开山镐、归营符、降尘丹等确定性物品配方。初始坊级、成本按 PRD §7A 导入。无品级器纹和降尘丹的 qualityCode 必须为空；铁胚品级由固定产物定义确定，不接受客户端任意指定。

后续随机器纹增加版本化 `craft_recipe_random_output`（recipe_id、asset_id、weight），七维固定等权；钱包处理器不存在时禁止启用。装备配方增加蓝图、可用铁胚品级、器纹槽和成品实例契约，打造资格由具体配方决定，不能由新六档品级名称隐式推导。永久强化用专门 unlock/state handler，不能伪造成堆叠物品。

引用检查覆盖配方成本、产物、品级、蓝图和等级解锁，物品详情反向查询“产出配方/消耗配方”。停用物品、品级或配方时阻止仍启用的悬空引用。

## 4. 玩家模型

一期复用资源域玩家 ID，经身份适配层映射为统一 `PlayerContext`。表不能新增另一套无法对应的玩家身份。

| 新增表 | 主键/关键唯一键 | 内容 |
| --- | --- | --- |
| player_inventory | (environment, player_id) | inventory_version、状态；作为玩家物品总锁 |
| player_item_balance | (environment, player_id, asset_code) | quantity；数量为 unsigned bigint |
| item_request | (environment, player_id, actor_id, request_id) | payload_hash、状态、固定 release_id、target_time、响应和 HTTP 状态 |
| item_transaction | id；索引玩家+时间+id | 业务类型、来源、操作者、版本、关联资源事务 |
| item_ledger | transaction_id + 序号 | 物品、变更前后与 delta |
| item_grant_claim | (environment, player_id, source_type, source_id) | 奖励幂等标记、奖励内容快照及 hash |
| item_pending_grant | id；来源+条目唯一 | 应发、已领取、待领取数量、settlement_id、状态 |
| player_workshop | (environment, player_id) | level、workshop_version；初始 1 级，仅在新玩家初始化时创建 |
| player_blueprint_unlock（外部蓝图阶段） | (environment, player_id, blueprint_code) | 来源与解锁时间，不是物品余额 |
| item_migration_record | (environment, player_id, migration_version) | 迁移来源、审计、执行结果 |

所有数量 API 使用规范十进制字符串，上限为既有资源域可支持的 2^63−1；客户端不得用浮点计算大数量。配置 holdLimit 通常远小于这一值。

临时战利品由权威出征结算持有，不能直接混入营地余额。未来装备用 `player_equipment_instance`，永久强化用专属账号状态。普通配方按坊级解锁，外部蓝图阶段才启用解锁表；本期不提前伪造实例能力。

## 5. 鉴权与写入边界

引入共用 `requireAdminContext` / `requirePlayerContext`：输出 actorId、kind、environment、allowedConfigSets、permissions。分别定义 `items.read/write`、`qualities.write`、`inventory.read/adjust`、`recipes.write`、`workshop.read`，发布复用审核/发布权限。

现有配置路由存在没有显式鉴权的路径，不能只在新物品保存接口加权限而让同一物品通过发布入口绕过。M1 必须覆盖物品编辑、校验、变更单、发布整条写链路；若正式账号尚未接通，只运行本机开发模式，不接受匿名写入。

开发身份沿用已配置的同一开发账号和显式启动开关，扩展权限须通过明确的开发初始化记录；不得在登录时自动给所有账号加权。Cookie 范围覆盖需要的管理 API，HttpOnly、SameSite 与同源校验保持一致；不把管理凭据暴露给客户端。

### 使用请求

```json
{
  "itemCode": "resource_pack.wood.lower",
  "quantity": "5",
  "expectedInventoryVersion": "17",
  "expectedResourceVersion": "28",
  "expectedReleaseId": "opaque-published-release-id"
```

Header：`Idempotency-Key`，身份在会话或既有 Bearer token 中。场景由服务端确认，客户端传 `camp` 不能视为可信。

## 7. 配置版本与发布

1. 保存时锁配置集，比较实体 revision，事务写物品/品级/i18n；配置集修订递增，旧审核失效，记录快照与审计。
2. 编译时校验品级引用、适用范围、所有效果目标、保护约束、图标/文本引用、持有上限和协议能力。
3. 基础模块增加 `itemQualities`、`itemQualitySchemes`、`itemDefinitions`；配方及坊级解锁进入同一发布的 economy 模块；保留旧 `assets` 结构。声明 `inventorySchemaVersion` 和最小能力版本。
4. 复用不可变产物与 hash/ETag。运行服务按配置集和明确发布 ID 载入，不混用最新草稿。
5. 明确环境到配置集/渠道的绑定；现有 development 渠道只有一个活动指针，不能默认它同时代表所有配置集。若后续多配置集并行在线，先扩展渠道键，不复用错误指针。
6. 发布指针切换与请求固定版本必须在一致的锁协议下完成。操作开始固定配置和服务端时间；续算继续使用已固定版本，不能每次重试读取“最新”。
7. 回滚重新构建并发布历史定义的兼容版本，不删除库存、不回滚已经完成的物品消费事务。

修改效果影响既有堆叠物品的未来使用；运行时确认 expectedReleaseId，不接受旧版本界面直接使用新效果。展示缓存失效时刷新后重新确认。

## 8. 跨域事务与幂等

### 8.1 ResourceService 改造前提

抽取接受外部连接的内部函数，例如 `settlePlayerInTransaction(connection, player, targetTime)` 和 `applyResourceDeltaInTransaction(...)`。公开资源 API 继续通过原入口编排，不能在物品事务中调用会自行提交的 `ResourceService.execute`，也不能二次 HTTP 调自己。

### 8.2 锁顺序

所有资源与物品相关操作采用一致顺序：

1. 配置渠道读锁（仅需要物品配置的请求）；
2. 资源环境规则锁；
3. `resource_player` 行锁；
4. `player_workshop` 行锁（炼制/升级需要），随后 `player_inventory` 行锁；
5. 幂等/领取记录；
6. 物品余额按 code 排序锁定、待领取条目按 ID 排序锁定。

发布端只持对应配置锁，不再反向获取玩家锁；资源独立操作不获取渠道锁，从第 2 步开始。所有新库存操作也先取得玩家锁；避免使用、调整和领取采用不同顺序。死锁重试在事务边界进行，保持原请求号和参数。

### 8.3 使用算法

- 会话鉴权并查已完成幂等结果；同键不同参数 hash 拒绝。
- 取得锁，固定 item release、资源历史、目标服务端时间，再核对客户端确认版本和场景。
- 先按历史规则结算资源生产，再计算 `room = max(0, capacity - balance)`。
- `actual = min(requested, owned, floor(room / amountPerUnit))`；请求超出持有量按参数错误拒绝，只有容量不足采用部分使用。非批量物品 quantity 必须为 1。
- actual=0 返回容量不足和所需空余空间，不扣物品；已进行的合法生产结算可提交，响应必须返回更新后的资源状态。
- actual>0 时同事务写物品减少、资源增加、两个版本、物品与资源流水和最终幂等结果。
- 内部异常全部回滚；业务容量不足与系统异常分开处理。

### 8.4 离线生产预算续算

已有资源结算可能返回 202。物品请求需先记录固定配置/时间的 pending 状态；此阶段只推进合法资源生产，不扣物品、不加开包收益。相同请求号继续执行，最终一次提交物品与奖励变化。并发修改在 pending 期间返回 PLAYER_BUSY。

请求恢复返回 202 或原终态。不能在超时时自动换请求号；客户端保留原请求直到明确结果。普通配置发布不改变已接受 pending 请求版本，紧急暂停使用在最终提交前再次检查并可结束为拒绝。

紧急暂停另用 `item_runtime_policy(environment, asset_code, use_paused, reason, revision)`，只允许具备紧急控制权限的管理员修改并审计，不改发布快照。所有物品操作在玩家锁后、最终提交前按固定顺序读取该策略；暂停更新取得同一策略行排他锁，保证暂停与正在提交的使用存在确定先后关系。缺省策略行在启用物品时创建，不依赖不存在行的锁。普通 use_enabled 随配置发布，紧急策略只做拒绝，不更改收益数值。

完成响应和业务变更同事务保存。幂等记录不能在客户端可能重试期间被删除；一期不自动清理。奖励来源唯一约束单独存在，不依赖可清理的请求缓存。

### 8.5 炼制及升级事务

一期示例请求：`{recipeCode, count, expectedWorkshopVersion, expectedInventoryVersion, expectedResourceVersion, expectedReleaseId}`，count 为正整数字符串且不超过配方 max_batch。客户端不提交成本、产量、成功率或成品品级。服务端从固定版本配方推导；场景限定为权威营地状态。

预览返回逐项账本来源、单次与总成本、结果及剩余容量、各状态版本，不只返回一个“材料足够”。确认接口按统一锁顺序校验版本、配方可用性、坊级/蓝图、所有余额、产物持有上限。

`count` 次确定性炼制采用整批全成/全拒绝：成本乘次数、产量乘次数均用 BigInt 并验证范围；持有量加全部产物不得超限。与开包部分成功不同，不自动缩减次数，不转待领取区。输入与输出相同 code 的循环配方一期禁止；重复成本在配置阶段合并或拒绝，不在扣款时重复遗漏。

结算生产完成后，在同一 MySQL 连接内扣资源/材料、加物品，写 item_transaction（craft）、全部 item_ledger 与关联 resource_transaction；修改实际受影响的状态版本，保存原请求结果。后台和 C 端可由同一请求号追踪成本与产物。请求命名空间统一，payload hash 包含 operationKind，防止 craft 与 use 复用同键。

长时间生产续算沿用 §8.4：pending 固定配方发布 ID、次数、目标时间及已确认条件，完成前不扣炼制材料。已经接受的请求恢复时区分自己推进产生的新版本与外部修改，不能用最初 expectedResourceVersion 拒绝自己的续算。并发外部写入受 PLAYER_BUSY 保护。

升级请求只接受期望坊级/状态版本，目标固定为当前等级+1；上限24，费用仅灵木，不接受客户端附加任务或修士境界条件。扣灵木、更新 player_workshop 版本与等级、持久化需要的蓝图解锁、流水和幂等结果原子提交。当前未开通的高阶玩法只解锁可见定义，不自动标记为可执行。

品级与配方表属于同一发布，客户端不能混合旧品级字典、新配方成本。降低坊级门槛影响后续可炼制项，既有玩家坊级及物品不会回退。

### 8.6 后续随机与装备执行边界

- 随机器纹必须先接权威灵石钱包，复用同一玩家总锁；钱包锁放在 workshop/inventory 之前，所有钱包联动操作遵守同一顺序。不能调用独立钱包 HTTP 扣款再发物品。
- 为保持七种结果严格等权，不能过滤已满库存的器纹后重抽。随机单次炼制前保守校验七种可能结果均有空间，任一满额则拒绝并提示整理；首期随机配方不允许批量，后续批量另设计容量策略。
- 不对客户端预览具体随机结果。首次请求固定服务端随机种子/结果计划及配置版本，pending 中加密或受服务端保护存储；实际发放与最终结果提交一次。刷新、重试、进程恢复必须复用已固定结果，不再次抽取。
- 随机计划固定只保留服务端状态，不扣费、不向客户端披露结果；最终事务失败时可按原计划重试，禁止通过试探库存或余额错误泄露结果。
- 装备打造依赖实例表及100仓位检查，成品品质来自合法铁胚，槽数来自蓝图，类型来自玩家提交且实际拥有的器纹；两枚同类按数量2扣除。费用依品质显式配置，特装固定品质需限制可选铁胚，不能与输入矛盾。
- 探灵灯/行营阵盘使用阶段唯一约束与前置阶段校验；永久状态与材料同事务，运行中的出征继续读取启程快照。此处仅定义扩展边界，M2 不开放未实现处理器。

## 9. 发奖与待处理

受信任 RewardGrantService 固定来源、奖励明细和配置版本，通过 `item_grant_claim` 去重。数量进入 balance 或 pending 的总和必须等于应发总数。

领取待处理条目时锁定来源和余额，只领取当前能容纳部分，更新剩余；并发领取唯一结算一次。待处理物品继续占据结算状态，不计作已持有数量，也不能直接当普通仓库使用。任务唯一物重复获得的去重语义由来源定义，不能产生两个唯一实例。

后台调整与正常发奖共用数量校验；原因必填、余额不能负、不能绕过持有上限。特殊补偿需要另建明确策略，不提供绕过全部规则的万能开关。

## 10. C 端与迁移

- `InventoryRepository` 负责权威快照、请求 pending、版本/错误处理，UI 不直接加减在线库存。
- 客户端原子切换一整套物品/品级配置；失败保留上次有效展示缓存，在线操作仍由服务端校验，不能将离线配置当写入依据。
- 百宝库从服务端数量与发布字典组合显示；任务保护、分类、品级文字与颜色来自配置。
- 发布或过期响应导致 CONFIG_CHANGED：刷新配置/快照、重绘预览，用户重新确认。
- 对 `game.gd` 中所有 `profile.inventory` 写入列清单：携带、归营、食物、归营符、任务奖励等，逐个迁移并关闭旧写入口。未迁移路径不得同时写在线库存。
- 首期开发使用独立在线档；正式迁移必须有服务端认可的来源、白名单、上限和一次性 migration record。不能把任意客户端 JSON 作为可信资产导入。
- 玩家所在场景由服务端出征会话决定。M3 需要接入这一上下文；在此之前在线测试玩家可限定为服务端标识的营地测试会话，不承诺野外行为可用。

M2：事务重构先于使用接口；实现玩家锁、幂等、资源联动、来源去重、待处理及运营查询，并完成确定性炼制与坊级升级事务。

## 12. 验证计划

- 单元：同名不同体系、无效颜色、分类不适配、保护约束、holdLimit、批量容量计算、整数边界。
- MySQL：并发保存、审核失效、物品和资源事务回滚、死锁重试、同键重放、同来源重复奖励、跨玩家/跨环境拒绝。
- 发布：旧 assets 消费者兼容、新字典完整、引用缺失阻断、运行时不读草稿、跨版本确认拒绝、历史请求返回原结果。
- 接口：鉴权/同源、字段错误、分页上限、无效数量、库存不足、暂停使用、pending 恢复。
- C 端：对 PRD Q01–C03 及 F01–F10 逐项验收（后续阶段用例在该阶段执行），尤其满仓、断网、实际百宝库、归营重放，不以 HTTP 200 单独判定成功。
- 炼制：已知配方精确扣费、跨账本回滚、整批拒绝、等级升级去重、相同材料并发竞争、暂停配方与版本冲突、planned配方拒绝。随机配方另验证固定结果恢复和不因库存改变概率。
- 回归：现有资源 35 项测试（当前基线数量）、剧情与配置发布检查、类型检查、lint、生产构建。新增测试数量不固定，以验收覆盖为准。
- 可观测：记录请求号、玩家/环境、版本、事务耗时、失败码；监控重复冲突、待处理积压、异常回滚。日志禁止写入 token 和完整会话凭据。

## 14. v0.2 依赖与落地顺序

1. M1 品级、物品定义、明确成本与产物的配方、1–24坊级/解锁配置及发布校验。

## 交易行售卖配置（2026-09-17）

物品目录编辑新增“允许在交易行售卖”，对应 `item_definition.is_market_sellable` / API `isMarketSellable`。默认false，旧数据迁移后不自动开放；可按允许/禁止筛选并查看独立列。每种物品单独配置，不按分类或品级自动推断。

任务物品和受保护物品不能开启；改为受保护或任务分类时界面会关闭开关，服务端仍独立校验，不能靠直接调用API绕过。是否允许丢弃与售卖为独立开关，禁止丢弃本身不代表禁止交易。

使用现有配置修订、审计与审核发布流程，导出至 base.itemDefinitions；开关只表示物品种类准入。将来的上架服务仍必须检查发布配置启用状态、绑定/穿戴/锁定/数量等实例条件；尚未实现玩家交易行、手续费、定价或成交事务。配置保存不等于玩家端已能交易。
