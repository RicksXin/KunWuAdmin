# 修士系统技术方案

版本：v0.1；日期：2026-09-17；状态：H1 配置管理已实现，H2–H4待开发；实际交付边界见 `09_修士配置开发记录.md`。产品范围见 `07_修士系统PRD.md`。

## 1. 现状与设计原则

复用现有 MySQL、Drizzle、配置集修订、实体审计、审核及发布模块；不新建第二套修士配置仓库。

现有 progression 表是配置，不是玩家存档。Godot `profile.roster` 和本地钱包不能直接当成可信在线余额。既有资源服务的杂役与修士是不同业务实体。

配置、实例、战斗快照三层分离：配置描述规则；实例保存已经发生的成长；战斗快照固定一次出征的属性和技能。

## 2. H1 配置数据

### 复用

| 表 | 改造范围 |
| --- | --- |
| hero_template | 编辑名称、头像、初始职业/灵根/境界/等级；按修订保存 |
| career + career_growth | 初始七维及每级千分位成长，父子表原子编辑 |
| spiritual_root | 初始/成长百分比、排序；独立于物品六档 |
| realm | 等级范围、顺序与突破关系；仅启用目标版本范围 |
| level_cost | 明确 level 表示目标等级；迁移前核对现有消费者，禁止隐式改变列语义 |
| career_skill / hero_template_skill | 阶段技能引用及固定三个槽位 |
| i18n_text | 与中文名称编辑同事务保存 |

### 新增

- `cultivator_rules`：config_set_id、code、max_level、fixed_roster_codes、灵息周期/上限、还魂公式参数、专精重置费用、revision/status。
- `career_route`：config_set_id、code、initial_career_code、parent_route_code、stage、career_code、next_route_code。筑基每初始职业两分支，结丹每分支唯一目标。
- `cultivator_breakthrough_rule`：source/target realm及等级、路线条件、结构化任务/试炼条件、升级费用是否包含、typed costs、一次性七维增量。
- 条件只接受版本化白名单，例如 quest_completed/trial_completed/in_camp/alive；禁止后台任意 SQL/脚本。
- typed cost 为 currency/resource/item + 稳定编码 + 正整数数量，魂晶/灵石/灵晶不能互相替代。

费用未接入对应权威钱包/库存时配置标记 planned，发布器禁止导出为可执行动作。

## 3. 保存、校验与发布

保存锁配置集 → 比较实体 revision → 校验引用 → 写父子表/i18n → 写实体快照及带 actorId 的审计 → 增加配置集修订 → 原审核失效。

职业和升级费用整组提交，避免逐行修改期间出现半套曲线。数组排序按稳定 code/等级/技能槽位确定，保证构建可重现。

发布前检查：

1. 四个初始位置引用的模板存在且初始状态合法；初始职业、灵根、境界、头像/名称引用可解析。
2. Lv1–30范围连续，无重叠和空洞；每个可达升级目标有唯一成本。
3. 职业路线无循环、无跨初始职业串线，分支数量及阶段正确。
4. 每个可达职业阶段恰好三个启用技能，技能类型和策略合法。
5. 突破源/目标与境界一致；费用全为正数，资产类型与处理器匹配，任务/试炼条件可解析。
6. 灵根倍率为正，计算中间值不溢出；还魂和灵息参数有边界。
7. 降低上限、移除路线、禁用被实例使用的定义必须走兼容性报告，不能直接破坏旧实例。

沿用 `progression` 发布模块，增加 rules/routes/breakthroughRules；必要时增加模块 schemaVersion/能力声明。旧客户端不认识新契约时不得部分应用。

## 4. H2/H3 玩家数据

| 表 | 关键字段与用途 |
| --- | --- |
| player_cultivator_roster | environment/player_id 唯一、roster_version；全队互斥锁 |
| player_cultivator | instance_id、owner、template_code、root、realm、level、route、HP、灵息、version、来源release |
| cultivator_growth_segment | 实例、职业/路线、等级起止、累计升级次数、固定成长率/灵根倍率及已入账增量、release_id |
| cultivator_breakthrough_record | 实例、突破阶段唯一、试炼/任务凭据、增量、费用、release_id |
| cultivator_skill_strategy | 实例+槽位唯一、skill_code、auto_enabled、允许的策略字段、revision |
| cultivator_request | 环境+玩家+请求ID唯一、payload_hash、固定release、状态及响应 |
| cultivator_ledger | request、actor、原因、实例前后版本、成长变化、钱包/物品交易关联 |
| cultivator_grant_claim | 环境+玩家+来源唯一；初始化及合法发放防重复 |

装备只保存物品实例引用，不复制装备库存；任务/试炼凭据来自权威事件或任务状态，不接受客户端布尔值。

历史分段应保存数值快照。若直接对同一段使用新成长率重算旧次数，会追改历史：规则版本改变时必须封存旧段，新段从当前累计状态继续。计算保持整数/有理数精度，按策划分段取整，不逐级丢小数。

## 5. API（拟议，尚未实现）

后台统一前缀 `/api/admin/cultivators`：workspace、templates、careers、roots、realms、rules、routes、玩家名册与流水。配置编辑携带 configSet 和 revision；玩家调整需独立权限和原因，不能把模板编辑当玩家改值接口。

C端前缀 `/api/game/v1/cultivators`：

- GET roster / detail：权威版本、当前可执行动作及禁用原因。
- POST quote：升级、突破、还魂、重置的预览；不扣款。
- POST level-up / breakthrough / respecialize / revive / emergency-revive / strategy。
- 写请求携带 Idempotency-Key、expectedRosterVersion、expectedInstanceVersion、expectedReleaseId；玩家身份由会话解析。
- 预览不是授权；执行时重新校验位置、存活、锁定、任务、库存与费用。

错误区分版本冲突、资产不足、试炼未完成、出征锁、达到上限、配置未就绪，返回可读原因；不能将所有失败显示成“没有权限”。

## 6. 原子性与锁顺序

跨资源/钱包/物品/修士采用同一 MySQL 事务边界。调用链必须传递同一连接，不得分别调用两个已提交的服务后拼接成功。

实施前统一所有参与服务的锁顺序，建议：玩家操作锁 → 钱包/资源账户 → 库存聚合锁 → 名册锁 → 实例ID排序锁 → 任务凭据。升级、突破、还魂、出征结算必须全部遵守同一顺序；现有服务若不兼容，先改造事务适配器。

执行步骤：认证 → 幂等键和请求摘要 → 固定可用配置版本 → 获取锁 → 校验版本及前置条件 → 计算 → 扣资产/物品 → 写修士及成长 → 写流水/请求响应 → 提交。

- 相同请求同参数返回首次结果；同键异参409；不同请求同旧版本只能一个成功。
- 批量还魂全成全败；免费还魂必须锁全队聚合状态，避免两次请求分别复活两人。
- 一次性突破按实例+阶段唯一，防止重复追加增量。
- 不在事务内调用外部网络；如果资产不在同一数据库，不能用顺序HTTP调用伪装原子事务，应先定义协调方案再开放功能。

## 7. 灵息与战斗

灵息结算使用服务器时间；保存逐人锚点及不足周期余数。营地/出征切换时先结算上一位置时间，再切换锚点；不把野外时长计为恢复。满值不囤积未来恢复次数；章节回满按结算ID去重。

出征时固定成员、配置release、成长结果、装备实例与技能策略；培养和换装在出征/待结算中禁用。既有CombatSnapshot不受后续发布影响。战斗结果必须通过可信结算写入，客户端不能直接提交最终HP和奖励余额。

## 8. C端迁移

- 在现有 Game 和 ConfigRepository 上接API，正式名册和营地入口消费同一状态，保留现有UI布局。
- 旧本地存档先备份、标识版本和来源。开发导入只允许开发身份；正式账号不直接相信本地等级/余额。
- 每玩家迁移标记唯一，初始化与旧档导入互斥。禁止初始化四人后再导入形成八人。
- 在线失败保留展示缓存，但禁止本地扣钱/升级后等待“补同步”。
- 配置下载成功与修士操作在线化分别验收；改模板不能宣称既有修士同步改变。

## 9. 验证与实施顺序

H1先完成职业ID映射清单与配置导入，再做固定导航、表单、接口、校验发布和新旧模块兼容测试。

H2准备权威魂晶钱包及玩家实例，验证边界升级、并发、回滚、重试、免费还魂互斥、灵息时间边界。

H3等灵石钱包、丹药库存和任务/试炼权威状态接通后，再开放筑基/结丹和专精重置。

H4在真实Godot营地完成“名册预览 → 执行 → 钱包/物品/修士同步 → 重启恢复 → 出征快照”的端到端验证。

H1配置管理已落地，未修改Godot存档。下一步先补齐正式技能与任务绑定，再推进权威实例；随机招募暂不纳入。

## 形象模板修订（2026-09-17）

- `hero_template` 新增 `appearance_code`、`name_pool`（JSON）、`growth_focus`、`growth_modifiers`（JSON 七维千分倍率）。旧行空值由后台兼容读取；旧覆盖属性保持不变。
- 模板 `code` 为稳定引用，`nameKey` 对应原型名称；个人姓名保存在实例，不能作为模板唯一键。形象编码是视觉引用标识，允许多个成长模板共用形象。
- 培养规则保留 `fixedRoster[4]` 模板引用，新增 `fixedNames[4]`；允许重复模板。初始化幂等按玩家+队伍位置，不能按模板去重。固定姓名优先，否则姓名池等概率选取一次并保存；允许不同实例同名。
- 每级成长 = 职业千分成长 / 1000 × 模板千分倍率 / 1000 × 灵根成长百分比 / 100。累计分段后取整，模板倍率也需进入未来成长账本快照；不能重算历史。
- 发布契约 `cultivatorConfigVersion=2`，模板新字段进入 progression.heroTemplates，固定名进入 cultivatorRules；`cultivatorRuntimeEnabled=false` 保持到权威实例与 C 端接入完成。
- `cultivators:setup` 仅升级 v1_0 仍保留旧个人姓名且尚无形象配置的种子行，写修订与审计；保留稳定编码和自定义行。补充降魔禅修示例，不发布版本。

## 普通与优秀模板配置（2026-09-17）

`hero_template` 新增可空 `template_class` 与 `acquisition_weight`，API 读取旧行默认为 common/0，旧版本不会意外进入随机池。新模板支持 common/excellent 分类与0–100000整数权重；0不参与默认渠道获取。启用状态且同 careerCode 的正权重归一化计算概率；不推断职业概率，固定初始队伍不受影响。字段随 progression.heroTemplates 导出，runtimeEnabled仍为false。

本次先实现默认渠道模板权重，尚无多渠道权重表、获取API或玩家抽取事务。模板技能方案、嘲讽、抗性、治疗与攻击频率仍待实现。

初始化种子来自 `server/domain/cultivators/templates.ts`，共12个模板。仅自动迁移尚未分类的旧种子行，保持初始实例引用、姓名池、头像、灵根和启停状态；重复运行不覆盖已配置模板。七维倍率为待实战校准的草稿，不代表技能效果。

## 按模板配置百分比

修士模板页面增加“模板获取概率”，按职业同时编辑所有启用模板，精度0.01%，合计必须100%。不强制普通/优秀固定比例；0%不参与获取。PUT /api/admin/cultivators 接受配置集、配置集修订及完整职业概率组，使用整数基点（10000=100%）存入原权重字段。服务端检查合计、重复项、完整成员和并发修订，事务内写修订、审计并使旧审批失效。旧权重用最大余数法转换为百分比，总和保持100%；原全零池需手动分配。停用模板仍按原规则排除并重新归一化；固定初始队伍不受影响。
