# 物品系统实施梳理

日期：2026-09-17。本文为下一阶段实施建议，不代表已实现或已上线。

后续需求与设计以 [物品系统 PRD](04_物品系统PRD.md) 和 [物品系统技术方案](05_物品系统技术方案.md) 为准，已补齐品级体系与阶段验收。

## 1. 已有基础与缺口

- `db/schema/base.ts` 的 `game_asset` 已具备稳定 code、名称键、类型、品质、图标、堆叠上限、重量、存放位置与保护/丢弃/交易标记；奖励包和掉落引用可复用。
- `server/compiler/config-compiler.ts` 已将资产定义编译进基础模块；物品配置优先接入现有配置集、校验、审核和发布流程，避免再建第二套定义。
- `server/services/config-query.ts` 当前只提供“资源与物品”列表查询，物品完整编辑接口、引用检查和专门页面尚需实现。
- 当前资源域拥有独立的玩家状态、发布历史和流水，不能把物品配置发布误认为资源规则发布，两域需明确环境与版本对应关系。
- 相邻 Godot 工程 `scripts/autoload/game.gd` 仍直接修改 `profile.inventory`、出征携带物和归营战利品；当前应视为本地逻辑，不能承诺后台修改后所有场景自动同步。
- 现有资源结算可复用事务和幂等设计，但不能以两个独立 HTTP 请求串联“扣道具”和“加资源”。

## 2. 物品边界

| 类别 | 存储与行为 | 建议阶段 |
| --- | --- | --- |
| 普通材料、加工品 | 按 item code 累计数量，用于任务与制作 | 一期 |
| 消耗品、食物 | 按数量持有，具有明确使用场景与效果 | 一期 |
| 资源包 | 开启后进入资源余额或钱包，本身仍是物品 | 一期先接已有资源域；灵石包待钱包事务接通 |
| 任务物、唯一核心 | 受保护，任务逻辑可合法消耗，禁止手动丢弃和分解 | 一期 |
| 装备 | 独立实例，包含词条、装备/锁定状态 | 二期 |
| 蓝图 | 永久解锁记录，不能按普通可堆叠物品处理 | 二期或与制作系统协同 |
| 五类生产资源 | 继续由现有资源域管理，不占背包 | 复用 |
| 灵石、魂晶 | 公共钱包，不能与生产资源混用 code 或余额 | 后续接入或一期明确事务适配 |

历史策划规定玩家不能出售物品；本期不增加出售、回购或玩家交易功能。

## 3. 后台页面

主导航统一增加一个固定“物品”入口，所有页面共享相同入口与顺序。

二级页面建议：

1. **物品目录**：按名称/code、分类、品质、状态筛选；列表只放图标、名称、分类、品质、持有上限、状态与编辑入口。
2. **玩家库存**：查看玩家已持有、临时战利品、待领取物品；后台调整须有原因、数量预览与审计。
3. **物品流水**：获取、使用、任务消耗、丢弃、归营、后台调整的前后数量、请求号与业务来源。

编辑采用抽屉或独立详情。基础字段默认展开，使用效果、存放规则、引用关系按需展开。版本校验、审核和发布复用现有流程，不在目录页堆放大段技术字段。

## 4. 配置字段

复用 `game_asset`；数据库迁移需增量完成，不重建已有资产或改动稳定 code。

- 基础：code（引用后不可改）、名称/描述、图标、分类、品质、启用状态、排序。
- 库存：存放区域、堆叠限制、账号持有上限、唯一性、重量、保护标记、可否丢弃。
- 使用：是否可使用、营地/野外/战斗场景限制、单次/批量支持、效果类型、目标、数量。
- 引用：任务、奖励包、掉落表、配方等引用关系。

**堆叠限制与账号持有上限必须区分**。策划中的材料 999、加工品/普通消耗品 99，以及资源包分档上限属于每账号每 ID 总量约束，不得通过新增堆叠绕过。

效果采用服务端白名单结构，例如 `grant_resource`、`grant_currency`、`unlock_blueprint`；只有已接通且经过校验的效果可以发布。不能上传任意执行脚本或由客户端自行指定奖励数量。

## 5. 玩家数据与接口建议

以下为设计建议，尚未创建这些表或接口。

- `player_item_balance`：玩家、环境、物品 code、数量、版本；同环境玩家和 code 唯一。
- `item_transaction` / `item_ledger`：业务请求、来源、原因、前后数量、关联资源流水。
- `item_request`：幂等请求结果，网络重试复用原请求号。
- `item_pending_grant`：无法立即入库的待处理奖励及领取状态。
- 装备实例和蓝图解锁分别建模，避免塞入数量表。

接口分为后台目录编辑/引用检查/玩家库存/调整/流水，以及 C 端库存同步/使用/丢弃/领取待处理奖励。任务奖励与掉落由受信任的服务端业务调用，不能提供客户端自由发物品接口。

玩家身份从会话取得。C 端传物品 code、数量、请求号、期望状态版本；服务端检查拥有量、场景、配置版本和容量，再原子提交。接口返回权威库存与资源变化，C 端以结果刷新显示。

## 6. 必须先做对的规则

1. **开包原子性**：先结算资源生产，再检查容量，扣物品、加资源、写双边流水与请求结果在同一事务内完成；制定统一锁顺序避免与现有资源操作死锁。
2. **容量不足**：单个资源包完整收益装不下则不扣包；批量只使用能完整装下的个数，明确返回实际使用数和剩余数。
3. **物品获取超限**：无法提前拒绝的任务奖励、Boss 奖励与安全归营奖励进入待处理区，不能静默丢弃。待处理与本次结算绑定，不能变成无限仓库。
4. **保护物品**：任务物、唯一核心及策划指定保护物不能手动丢弃、出售、分解或因阵亡损失；任务提交消耗需有专用合法路径。
5. **出征隔离**：临时战利品与营地库存分开，归营或失败结算只入账一次。背包切换页面不触发重复发奖。
6. **配置版本**：已持有物品 code 不因改名而变化；禁用不删除库存；降低持有上限保留旧数量并停止继续入库。奖励生成时记录版本及内容，重复领取不能按新配置重抽。
7. **使用时点**：建议开包按操作时已发布效果计算，并在服务端确认结果中返回配置版本；若未来需要历史批次效果，需另加批次模型，不能隐式混用。
8. **离线与重试**：一期在线背包不允许断网后本地自行发奖/扣除再合并；保留未确认请求并通过同一请求号恢复。

## 7. 实施顺序及验收

### M1：物品配置

- 清点现有 code 与策划清单，明确 demo_d0 / 正式配置集的差异。
- 完成目录与详情编辑、字段校验、引用检查、版本发布。
- 首批选普通材料、一个食物、一个生产资源包、一个任务物验证，不一次导入全部装备。
- 验收：后台修改发布后，C 端实际读取相同版本、名称、图标、上限及效果。

### M2：在线库存与资源使用

- 完成库存、使用、受保护丢弃规则、后台调整、流水及待处理奖励。
- 与资源域实现同库事务；未接通的钱包效果不得启用。
- 验收：正常使用正确到账；容量不足不扣物品；不足、重复点击、并发、断线重试无重复发放或部分提交。

### M3：接入实际 C 端

- 在真实百宝库界面接入仓库服务，资源包与食物使用走服务端。
- 清点并逐项替换本地 `profile.inventory` 写入口，包括出征携带、任务、归营和失败结算。
- 明确旧存档到在线库存的迁移策略与一次性迁移标记；禁止客户端上传任意余额直接覆盖。
- 验收覆盖实际营地→出征→获取→归营→使用流程，不能仅以独立测试场景通过视为完成。

### M4：装备与制作协同

- 装备实例、词条、装备/锁定保护、批量分解、100 仓位与蓝图永久解锁。
- 配方成本与产物、分解返还与库存共用账本，避免奖励重复计入。

建议本次下一步先实施 M1，并用 M2/M3 的一个资源包使用流程证明配置和实际效果贯通。完整装备系统单独排期。
